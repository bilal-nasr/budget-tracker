# Category Management Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task, or the orchestrator's explicitly chosen execution workflow. Steps use checkboxes. Do not stage or commit; the owner commits manually.

**Goal:** Let each user add, edit, remove and restore their categories without losing financial history or exposing another account's data.

**Architecture:** Keep the existing `categories` table and its per-user defaults. Separate the complete category catalogue used to resolve history from active categories selectable for new entries. Enforce lifecycle and reference integrity in Postgres, expose authenticated zod-validated Server Actions, and add a Settings-linked manager using existing sheet and tile components.

**Tech stack:** Next.js 16.4.5 App Router, React 19.3, Supabase/Postgres 17, zod 4, next-intl, existing Base UI primitives, Vitest, pgTAP, Playwright. No new dependencies proposed.

**Spec:** The proposed design below implements owner item 1. Read `PRODUCT.md`, `CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/MOBILE-UX.md`, `DESIGN.md`, and `.impeccable/surfaces/src-app-locale.md`. This document is a proposal, not an owner-approved product decision.

## Proposed design and behavior

1. **Manager:** Settings → Categories → `/[locale]/settings/categories`. Expense/income segments, active list, Add category, and collapsed Archived list with Restore. Tap a row for its editor. Keep current tile glyphs, card/list geometry and `SheetShell`; use 44px controls, 16px inputs and thumb-reachable Save. Loading skeleton, retry/error, empty and preview states are required.
2. **Names:** Explicit English and Arabic inputs, both optional individually, at least one required. Blank becomes null; normalize runs of ASCII whitespace and NBSP to a single space and trim. Each stored name is 1–40 Unicode code points. Fallback displays the other language without automatic translation. Custom text remains plain escaped text. Names are isolated with `<bdi>`.
3. **Identity:** Eight existing tile motifs and `teal | oxblood | ochre`, accessible radio groups with translated motif/color labels. Live decorative preview accompanies the name. Kind is chosen on create and immutable afterward. Item 1 manages roots; parent IDs are not user-editable here. Position appends deterministically after existing siblings; no drag reorder in this item (the older Phase 4 reorder checkbox remains open).
4. **Default versus custom:** All defaults are ordinary user-owned rows and get the same edit/delete rules. No protected names, ID assumptions, origin backfill or automatic reseeding. Renames update labels on past transactions; amounts, dates, IDs and budget associations stay unchanged. Do not imply that old category names are snapshotted.
5. **Duplicates:** Reject a normalized name matching either existing name in its **same language**, same user, kind and parent scope, among active categories. English comparison folds ASCII A–Z; Arabic remains literal after whitespace normalization (no diacritic/alef folding). Across users, kinds and parents the same names are allowed. English text in one language field is not compared against the other field. Archived names may be reused; Restore can fail with an understandable duplicate-name message. Database unique indexes, not a preflight query alone, decide concurrent duplicates.
6. **Remove unused:** Confirmation explains permanent removal. A category is unused only if it has **no** transactions (including soft-deleted rows), fixed expenses, installments, budgets (including null-limit rows), or children. Remove only that category, never financial rows. Guard the direct database delete path too.
7. **Remove used:** Confirmation says it will be archived and kept in history. If a fixed expense or installment still references it, refuse with `inUse` and instructions to reassign it in the existing edit sheet or remove the template first; previously generated payments remain untouched. This includes paid-off installment templates. If it has any existing child categories, including archived children, refuse and explain that categories containing child categories cannot currently be removed. Keep the root and all children intact; no hierarchy management UI or subtree operation is proposed. With only transactions/budgets remaining, archive rather than delete. No historical reassignment or merge wizard is proposed.
8. **Archive consequences:** Exclude from new transaction/template selectors, contextual Add and new positive budgets. Keep in historical lookups, Activity filters, and budget rows wherever a limit or spending exists. **Existing budget limits continue to carry forward until explicitly cleared**; show archived status and permit clear-only editing of an existing limit. Never silently cancel a budget or erase its schedule while removing a category. Restoring re-enables selection and does not recreate cleared limits. This is the simplest behavior compatible with existing budget history, but needs clear confirmation copy.
9. **Existing archived references:** A historical transaction may keep its unchanged archived category when editing date/note/amount or restoring a soft deletion. Selecting a different archived ID or creating a new entry with it fails server-side. Existing fixed/installment rows pointing to an archive from a previous/manual state can be edited to an active category; payment fails with a useful category-unavailable message until reassigned. Their unchanged archived reference may remain while editing unrelated metadata, but does not grant permission to make a new payment.
10. **Salary:** Prefer deterministic `(position,id)` first active income root rather than name-based selection. With the default seeds that is Salary, including after a rename; removing it uses the next active income root. If none exists, `receiveSalary` returns `categoryUnavailable`, with EN/AR guidance to create or restore an income category in Settings. No invisible recreated category. A dedicated salary-category preference is a future alternative, not required for this item.

### Alternatives and tradeoffs

- Reassign all transactions before deletion would rewrite historical categorization and require resolving budget schedule conflicts. Archive preserves history with less UI and no money movement; recommend it.
- Auto-moving fixed/installment templates during removal adds a multirow transaction and another target selector. Manual reassignment through existing sheets keeps the removal contract small and explicit, at the cost of an extra step.
- Auto-ending budgets on archive needs a timezone/month policy and decisions about future schedules. Explicit clear-only editing preserves current semantics; the user must clear a carried budget separately.
- Soft-delete every category is simpler internally but retains truly unused clutter forever. Hard-delete unused/archive used offers useful deletion without financial loss.

## Contract with item 2: optional transaction itemization

- Item 2's meaning is settled: one expense may optionally contain description-and-amount child item rows, with an optional unitemized remainder. The owner's example is one $50 expense to their sister comprising $20 phone credits and $30 for her. These are transaction items, not category children.
- The parent transaction alone owns `category_id`, currency, wallet and the ledger amount. Item rows have no category selection or independent ledger/budget effect. Item 2 owns its separate child-item table, validation, atomic parent/items writes and item-sum/remainder rules; do not reuse `categories.parent_id` for itemization.
- Shared `Category` adds required `parentId: string | null` and `archivedAt: string | null`. `getCategories()` returns all owned roots and existing child categories, including archived; `categoryById` indexes the complete catalogue. `categories` keeps that meaning throughout the provider so itemized transaction details can resolve the parent category after archive.
- Add pure helpers in `src/features/categories/schema.ts`: `activeCategories(categories: readonly Category[], kind: Category["kind"], parentId: string | null = null): Category[]` and `categoryOptions(categories: readonly Category[], kind: Category["kind"], currentId?: string): Category[]`. Creation options are active roots; transaction editing may retain its unchanged current category, including an archive or legacy child. Item 2 uses the same parent-transaction selector rules and does not introduce hierarchical presentation or subcategory CRUD.
- Existing category hierarchy is supported defensively by item 1, independently of item 2: duplicate scope remains `(user_id, kind, parent_id)`, owner/kind/depth/self-parent checks remain enforced, kind/parent changes stay locked, and removal/archive of any root with child category rows is blocked. No hierarchy UI, subtree operation or recursive deletion belongs to either item.
- Budget limits stay on category roots; existing child-category spending retains the SQL rollup already implemented. `buildMonthBudgets` filters `parentId === null`; `month_category_spend` continues reading archived categories. Itemization must count only the parent transaction amount once, without joining item amounts into category totals. No descendant filter expansion or child-category budget-allocation work is assigned to item 2.
- Coordinate migration ordering, transaction action/trigger edits, the transaction sheet/detail, category schema/helper/selector use, demo fixtures and EN/AR messages through the orchestrator. Category lifecycle/catalogue is a shared integration foundation; item 2's transaction-item schema is separate and has no category-hierarchy dependency.

## Review focus

- A removed category with only budget rows must retain all limits; the existing cascading FK makes this an easy history-loss bug (Task 1 SQL tests).
- A stale open Add sheet or direct API call must not post to an archived or another user's category (Tasks 1–3).
- Rename, archive and restore must preserve historical labels, unchanged archived edits and per-currency totals (Tasks 2, 4–5).
- Concurrent duplicate creation or reference insertion versus removal must serialize safely, including soft-deleted transactions and child rows (Task 1 concurrency checks).
- Long Arabic/single-language names, duplicate restore and no remaining income categories need understandable states without overflow or silent salary failure (Tasks 2–5).
