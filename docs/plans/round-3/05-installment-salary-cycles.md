# Installment Salary Cycles Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task after the orchestrator authorizes implementation. Steps use checkbox syntax. This dispatch authorizes investigation and this plan only; no product implementation, staging, commits, servers, migrations, worktrees, or additional chats. The owner commits manually.

**Goal:** Keep an installment's payment status attached to the actual salary receipt that funded its cycle, with an explicit action for another payment in that cycle, while preserving principal and expense history.

**Architecture:** Reuse tagged salary transactions as receipt events. Store each new installment payment's receipt ID, and an optional preceding-payment ID that expresses a confirmed extra payment. Validate cycle, override, ownership, and remaining principal together in the database; compute principal progress and cycle progress separately from one consistent read snapshot.

**Tech Stack:** Next.js 16.4.5 App Router, React 19, TypeScript, Supabase/PostgreSQL 17, zod, next-intl, Vitest, pgTAP, Playwright. No new dependency proposed.

**Spec:** Owner item 5 in the planning dispatch; the proposed design in this document, `PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/MOBILE-UX.md`, `DESIGN.md`, `.impeccable/surfaces/src-app-locale.md`. Round-3 orchestrator owns migration ordering and shared-file coordination in `docs/plans/round-3/README.md`. All policies below are recommendations, not owner-approved decisions.

## Review Focus

1. Crossing a month boundary without receiving salary must leave paid status unchanged; two genuine receipts on one day must create two distinct cycles.
2. Backdating an expense changes its reporting date, not its salary-cycle assignment; editing the salary wallet/amount must not rewrite older cycles.
3. Partial payments, installments without a monthly target, final small remainders, and extra payments must not produce negative needs or misleading paid-off labels.
4. Salary/payment undo, restore, and deletion of the installment must preserve all unrelated expenses and never silently reassign existing payments.
5. Concurrent normal payments, concurrent overrides, and retried salary confirmations must cause at most the intended number of transactions, even through direct authenticated database API calls.

## Proposed design/spec

### Receipt identity and cycle policy

- A salary receipt is an owned transaction with `source='salary'`, `kind='income'`, `deleted_at is null`. Category name, note text, wallet, calendar month, and ordinary income do not identify a receipt.
- **Proposed default: one account-wide cycle**, identified by the most recently recorded live salary receipt ID. Any genuine salary receipt, including a second receipt in the same month/day or a salary in another currency, advances the cycle for all installments. The app currently supports one configuration; do not invent multiple employer configurations in this item.
- Before any salary receipt, cycle ID is `null` (“Before first salary”). It is a real initial status bucket, so paying before setup is possible and remains paid until the first genuine receipt. Changing/clearing salary settings does not change the cycle; missing future receipts do not cause monthly automatic resets.
- Receipt order is immutable recording order (`created_at,id`), not `occurred_on`. On new salary inserts stamp a server timestamp under the per-user lock, strictly later than the maximum existing owned salary creation timestamp (including soft-deleted receipts), using `greatest(clock_timestamp(), previous_max + interval '1 microsecond')`. This avoids same-clock-tick ties/start-of-transaction timestamps reversing concurrent receipts. Existing timestamp ties are ordered deterministically by UUID during migration only.
- **Proposed default: bind payment to the current cycle at recording time.** The payment date remains editable/backdatable for Activity/budgets, but cannot choose/rewrite its cycle. Explain this near the date control. No historical cycle picker in this scope. Future backdated salary receipts, if introduced, likewise open a cycle when recorded, not at their accounting date.
- Same currency as the salary wallet is not required; installment payment wallets still must match the installment currency. A global status bucket carries no money amount and performs no conversion.
- If multiple salary configurations are added later, this proposal continues to use each actual receipt as a global boundary. A per-installment funding-source assignment would be a separate explicit schema/product decision; do not infer it by wallet or currency.

### Paid state, amounts, summaries

- Lifetime fields remain unchanged: `paidMinor = paidBeforeMinor + sum(all live linked expenses)` and `remainingMinor = totalMinor - paidMinor`. Pre-app paid principal is not a cycle payment.
- `paidThisCycleMinor` sums only live payments whose stored `salaryCycleId` equals the current cycle ID (null-safe equality). `cyclePaymentCount` controls whether an ordinary Pay is available; the latest such payment ID is the extra-payment concurrency token.
- `dueThisCycle(i) = monthlyMinor === null ? 0 : min(monthlyMinor, remainingMinor + paidThisCycleMinor)`. This keeps a final payment in the current cycle's planned total and avoids adding a new obligation after debt is fully repaid.
- **Proposed partial-payment policy:** the first positive payment records one payment occurrence and hides the ordinary Pay button. If the configured target is not yet covered, show “Part paid” with `paid/target`; use an explicit “Pay again” action to finish it. At/above target show “Paid for this salary”; with no target show that label after any payment. Lifetime paid-off takes precedence and offers no further payment.
- An extra payment always reduces principal and appears as a normal expense. Extra amounts do not inflate the planned installment amount, carry a paid badge into the next salary, or prepay future cycle badges. A payment below target does not make summary unpaid zero: `unpaid = max(0, dueThisCycle-paidThisCycleMinor)`.
- FixedSummary retains monthly fixed-expense behavior and its current planned-total meaning. Only its installment contribution changes to cycle math. Preserve default-wallet planning attribution and actual-wallet expense deduction; label that distinction in sheet help. Replace “All paid this month” with neutral “Nothing left to pay”/Arabic equivalent, and explain that installments restart after salary receipt. Do not change budgets/month reports to salary cycles.
- Examples (USD cents): total 120000, prior live payments 20000, monthly 10000. A 4000 current-cycle payment gives lifetime paid 24000, remaining 96000, cycle left 6000, Part paid, Pay again. Confirming an additional 6000 gives paid 30000, remaining 90000, cycle left 0, Paid for this salary. A new salary gives cycle paid 0 and due 10000 while lifetime paid/remaining stay 30000/90000. An extra 15000 in the prior cycle leaves 75000 principal; the next due remains min(10000,75000), not zero.

### Deletion, reversal, and editing

| Event | Proposed behavior |
| --- | --- |
| Delete/Undo current salary receipt | Current cycle becomes the previous live receipt, or null. Existing payments retain their original receipt links and remain historical expenses/principal reductions; do not merge them into the preceding cycle. The restored prior cycle's own payments determine its badge. Warn in salary deletion UI that installment statuses return to the prior salary. |
| Restore a salary receipt | Restore that original event at its original position. It becomes current only if it is the newest live receipt; no new receipt is inserted and payments are not moved. |
| Delete a non-current salary receipt | Current badge does not change. Historical payment links remain valid to the soft-deleted row. |
| Edit salary amount/wallet/category/date | Keep receipt identity/order. Require income kind and valid owned active wallet/category as appropriate; amount edit changes income accounting only. Do not change payment links. |
| Delete an installment payment | Remove its amount from lifetime and cycle sums. If the last current-cycle live payment is removed, ordinary Pay becomes available again; if others remain, retain cycle state and latest-live-payment anchor. |
| Restore an installment payment | Reactivate the same historical fact in its original cycle, subject to the existing aggregate principal cap. Allow historical restoration even if another payment now exists; it is an explicit Undo, not a new payment. Reject restoration that exceeds remaining principal with a specific error. |
| Edit installment payment | Preserve source/installment/receipt/override identity; allow valid same-currency amount/date/wallet/category/note edits. Recalculate principal and cycle amount; require expense kind. No new payment occurrence. |
| Delete installment | Keep all transactions and their cycle metadata; retain `ON DELETE SET NULL` for installment link. No source-tag rewrite, cascade deletion, or fabricated refund. |
| Add a refund/opposite ordinary transaction | It changes wallet accounting but is not a receipt cancellation/payment reversal automatically. Existing UI reversals are delete/restore. Explicit linked reversal records would be another feature. |

Deletion/restore can expose old paid states; explain this instead of using a second mutable “paid” flag. A same-cycle request ID whose transaction was deleted must return `requestAlreadyUsed`, not silently insert or restore it.

### Minimum data change and alternatives

**Recommended durable delta: two nullable columns on `transactions`, no new table and no balance/paid flags.**

1. `salary_cycle_id uuid null references public.transactions(id) on delete restrict`: receipt association for installment payment rows. Null represents before-first-salary. Validate referenced row belongs to the same user and is a salary income; retain association after soft deletion.
2. `installment_override_of uuid null references public.transactions(id) on delete restrict`: on a new additional payment, the latest live payment in this installment/cycle that the user explicitly acknowledged. This is a validated compare-and-set token, not proof of historical user consent. Do not backfill invented override acknowledgments for old rows. New ordinary payments have null; existing legacy multiple-payment rows can remain null.

Reuse transaction `id` as an idempotency key supplied as a UUID for one logical submission; no separate request table/column required. Add a current-receipt lookup index `(user_id,created_at desc,id desc) where source='salary'`, including deleted rows for monotonic stamps, and payment lookup index `(user_id,installment_id,salary_cycle_id,created_at desc,id desc) where installment_id is not null and deleted_at is null`. Use null-safe comparisons; no monthly unique constraint that would prohibit deliberate repeats.

Display-only status could use zero columns by comparing creation timestamps; that cannot retain an explicit association reliably across receipt deletion/restore and historical changes. One receipt-link column plus RPC-only protected special-transaction permissions is another valid design, but it requires a broader RLS/privilege rewrite to stop direct inserts bypassing an ephemeral override argument. The second column keeps intent inspectable by the existing invoker triggers and avoids that broad rewrite. A new salary_cycles table and persisted installment paid flag duplicate existing facts and are not justified here.

**Backfill proposal:** for each existing linked installment payment, select the latest same-user salary income transaction whose `(created_at,id)` is <= the payment's `(created_at,id)`, including soft-deleted salary/payment rows to preserve their recording-era association. Null if none. Do not use accounting dates or infer untagged Salary notes. Keep every amount/date/principal unchanged. Old ambiguous imported timestamps have only this deterministic best-effort reconstruction; report counts/ambiguities in migration review without outputting personal data. Backfill before enabling the new insert guard, in one migration transaction. Source-shape anomalies should abort for an explicit repair decision, not be converted/deleted silently.
