## Design/spec — currency proposals and confirmed Move UX addition

### Precision and denomination

**Recommend SYP precision 2, stored as integer qirsh: `SYP 1.00 = 100 minor units`.** Two decimal places preserve fractional prices and electronic/accounting amounts without inventing a cash-rounding rule. Fractional entry is allowed, not required. Display `SYP 12.50`, using the profile's digit preference; code stays `SYP` in both languages so it cannot be confused with LBP. `parseAmount("١٢٫٥٠", "SYP") === 1250`. Negative opening balances remain signed integers; individual transaction amounts remain positive with direction/kind supplying the sign.

Authoritative verification performed on **2026-11-04**:

- SIX is the official ISO 4217 maintenance agency. Its current List One XML (publication attribute `2026-09-17`) was read directly in memory: Syrian Arab Republic / Syrian Pound / **SYP / 760 / minor unit 2**. LBP also has ISO minor unit 2, illustrating why ISO metadata alone must not silently override this app's established whole-LBP storage policy. [SIX currency standards and current-list links](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html), [official current XML](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml).
- Syria's official national news agency reports Decree 293/2025 effective January 1, 2026, distinguishing old and new pounds and defining 100 qirsh per new pound. This is evidence of a denomination distinction, not an instruction to transform this database. [Official SANA decree report, December 31, 2025](https://sana.sy/en/presidency/2286703/).

**Recommend current/new-pound entry only in this release**, explicitly labeled “Syrian pound (new)” / “الليرة السورية الجديدة” in currency descriptions. Show contextual help on SYP wallet creation (also reached through onboarding) and Settings: “SYP uses the new Syrian pound. 100 qirsh = SYP 1.00.” / “تُسجّل مبالغ SYP بالليرة السورية الجديدة. كل ١٠٠ قرش = ١٫٠٠ SYP.” Keep that formula isolated LTR. Do not derive units from transaction dates, currency-code heuristics, banknote sizes, or entered magnitude. Do not convert old-pound amounts automatically. An old-denomination entry feature would need a separate explicit unit model and its own plan; the enum code alone cannot distinguish it. Confirm whether that capability is needed through the orchestrator's consolidated decisions.

Alternative: whole-pound SYP would mirror the current LBP UI and simplify cash entry, but rejects meaningful hundredths and creates an avoidable future data migration. Recommend against it. Do not use runtime `Intl` currency defaults to decide storage precision; the application registry is authoritative for its ledger.

### User-visible behavior

- Currency order: USD, LBP, SYP. Keep USD as the initial selection for a new wallet/empty app; never fall back to USD when an existing SYP wallet is selected. Existing wallets retain their stored currency.
- Wallet selection offers three codes with translated names/context. Onboarding reuses `WalletForm`; it does not need a second currency implementation. Settings currently has no reference-rate/default-currency editor: add the SYP unit explanation without inventing a global currency switch or SYP rate setting.
- Display every held currency separately. Home renders a list of held currencies (first at the existing 40px hierarchy, later rows 28px), Wallets has a group per currency, Activity has independent daily nets, Fixed has independent totals/unpaid values, Budgets can select SYP. Wrap/stack money rows; do not ellipsize money to squeeze three values into one line.
- A change to a different currency in an amount form clears the affected editable amounts and shows localized “Enter the amount in {currency}.” Preserve text when switching wallets of the same currency. Never divide, multiply, truncate, or reinterpret existing text automatically. For installments clear total, monthly and paid-before together on a currency change during creation; existing installments remain restricted to wallets in their locked currency.
- SYP has the decimal keypad and `inputMode="decimal"`; LBP retains `000`/numeric. Drive behavior from precision, not `currency === "USD"` or `currency === "LBP"`.
- Budget currency visibility includes active wallets **or** that month's budget/spend rows, so archived-wallet SYP spending does not disappear. Valid `?currency=SYP` is recognized, invalid/repeated values fail safely to the existing fallback; retain month query state when switching.

### Conversion boundary and cashier integration

**Recommend the narrower supported behavior for this round:** automatic/reference conversion remains USD↔LBP only. All SYP↔USD and SYP↔LBP wallet exchanges require two explicit actual amounts. A SYP→SYP move is an ordinary equal-amount transfer. No triangulation through USD/LBP; no approximate SYP total without an explicitly supported pair/rate.

- Keep `profiles.usd_lbp_rate`, `Profile.usdLbpRate`, `AppDataProvider.usdLbpRate`, integer `parseRate` and its bound specific to USD/LBP. Do not rename the database field to generic `rate` or reuse it for SYP. Existing rate values retain their meaning and prefill behavior.
- Retain the current internal `convertAtRate(minor, from, to, lbpPerUsd): number | null` interface for compatibility, but whitelist USD/LBP **before** arithmetic/identity. Reject every call involving SYP (including identity) with `null`. It is only a USD/LBP helper, not the same-currency transfer implementation. Add `supportsUsdLbpRate(from: Currency, to: Currency): boolean`, true only for the two different-currency USD/LBP directions. Document the legacy name and consider a later rename separately; there is only one production caller today.
- In Move, show rate controls and “Use rate” only when `supportsUsdLbpRate(...)` is true. “You received ({currency})” starts read-only, with an adjacent edit button enabling manual entry as confirmed below. For a SYP pair explain that no calculated rate is available and the actual received amount must be entered using that edit control. Clear received override and derived values when the currency pair changes; preserve raw manual received drafts across amount/rate changes within the same pair. Changing only wallet IDs within the same currency pair need not erase a valid received value.
- Do not send a `rate` for SYP. Server-side validation must independently reject a supplied USD/LBP rate for any unsupported pair before recording the transfer; UI hiding is insufficient.
- **Cashier item 4 contract:** consume the shared `Currency`, precision map, parser, formatter and pair predicate. Same-currency SYP purchase/change can use integer subtraction. If cashier requires a calculated cross-currency tender/change amount, reject an unsupported SYP pair with a localized explanation; do not call this converter. If cashier supports explicit manual legs, it may record SYP only when every actual amount is known and the complete event is atomic. A partially inferred SYP leg must block Save. The orchestrator must align one backend event/transfer helper with item 4 rather than creating competing SQL functions.

Alternative if automatic SYP conversion is an actual owner requirement: replace this narrow boundary with a separately approved directed `RateQuote = { base: Currency; quote: Currency; numerator: string; denominator: string }` where positive integer strings describe quote **major units per base major unit**. Compute `minor * numerator * 10^quoteDecimals / (denominator * 10^baseDecimals)` using BigInt and one half-up rounding at the destination; reverse only an explicitly selected quote, never infer a third pair. Rates need per-user pair keys, exact decimal/rational parsing, explicit denomination and freshness/source semantics, RLS and cashier rounding agreement. No rate values are proposed here. That expands schema/UI/testing substantially; do not implement it implicitly as part of adding an enum.

This wallet-to-wallet **Move** UX is owner-requested, overriding any earlier assumption that Received is immediately editable. It is separate from cashier tender/change; currency/rate proposals elsewhere in this document remain proposals. Apply the established UI skill during implementation, not this planning update.

Keep logical source-then-destination order in RTL, 44px minimum triggers/options, 16px text, wallet name plus an isolated currency code, and full accessible/discoverable selected/option text. A visually shortened trigger name must remain discoverable in the opened list and accessible name/description; keep currency visible. Source is excluded from destination choices; changing source preserves a valid destination or clears it if now identical. Preserve Add-money destination presets. Same-currency moves still use one amount with equal stored sent/received amounts and no Received editor/rate row.
- Cross-currency Received starts **locked with native `readOnly`**, retaining its label, readable/selectable value and focus semantics. Show the calculated amount only when the supported pair, source amount and rate are valid; otherwise show a blank value, not zero or an old value. A real zero conversion retains the existing too-small error. Put a 44px pencil button beside the field with the localized accessible name “Edit received amount” / “تعديل المبلغ المستلم”. Explain its locked/manual state with associated help; lock state must not rely on color or an unlabeled icon.
- First edit tap seeds a manual draft from the visible calculated value (or empty if unavailable), unlocks the field and focuses it. Keep this focus within the tap's user-activation path so the iPhone keyboard opens: commit the edit state synchronously before `ref.focus()` rather than deferring focus with a timer/animation frame. Repeated pencil taps only refocus, never reset an existing manual draft. Once unlocked, `receivedText` is the raw string owned by the user: typing, partial decimals, invalid drafts and deletion to `""` never fall back to a calculated value. Validate separately; invalid/empty received disables Save. Amount/rate changes within the same ordered currency pair preserve that draft.
- On supported USD/LBP pairs, **Use rate** explicitly exits manual mode, discards the override, recomputes and relocks. If rate is missing/invalid, it relocks blank with help directing the user to enter a rate or tap Edit for actual received; a valid manual amount remains saveable without a rate and sends no rate metadata. Source/rate changes update only locked calculations. On any ordered currency-pair change, clear the manual draft/override and relock before showing the new calculation or blank; never reinterpret an old value. Selecting another wallet in the unchanged currency pair preserves mode/draft. Entering same-currency Move removes/resets received state; returning to cross-currency starts locked.
- SYP pairs start blank/locked with “No calculated rate is available. Tap Edit to enter the amount actually received.” / “لا يتوفر سعر صرف لحساب المبلغ. اضغط على تعديل لإدخال المبلغ الذي استلمته فعلاً.” Edit enables the actual-received field; Save remains disabled until a positive valid amount exists. Keep **Use rate** absent for SYP pairs and never call the USD/LBP converter or save a SYP rate. USD/LBP with no rate has the same explicit manual escape path, alongside its rate input. Both sent/received amounts continue to be recorded through the existing single-transfer event contract.
